# Authoring contract

Load for creation, content assessment or revision. Establish the useful task, audience, trigger, required inputs, output, stop conditions and observable success. Prefer an existing owner over a competing entrypoint.

When a type-specific contract changes the work, read the [recipe selector](recipes.md) and only the selected recipe. Choose the method from the requested operation, the recipe from the target skill's job. A reviewer recipe does not replace this skill's assessment method; recipes do not grant writes or take over collection migrations. Existing skills keep their structure unless a demonstrated need justifies changing it.

- Ask what changes if each instruction disappears. Retain unique decisions and constraints; cut generic competence advice, repeated conclusions and ornamental examples. Rewrite vague qualities as observable requirements when necessary. No arbitrary token or line cap, numerical quality score or mandatory section count.
- Match form to the problem: define the required output for shape errors; put a repeatedly omitted requirement in an existing template; use observable conditions for conditional behavior. Prescribe exact steps where correctness depends on order; leave other methods adaptable without weakening safeguards.
- Keep rationale only when it prevents a concrete misreading. Preserve numbers, units, reversal conditions and failure behavior as well as the entrypoint's invariants. One example or preference does not establish a universal rule. Use do/don't distinctions and checklists only where they change behavior; do not repeat them in prose.
- Discovery metadata selects the skill; the body governs it. Keep shared authority, mandatory safeguards, routing and safe fallback in the entrypoint. Put conditional procedures in references, and substantial sub-specialties under their owning reference. Keep atomic invariants together. Every route names its condition, unique owner, direct link, missing-resource behavior and whether it augments or replaces parent work. Complete mandatory parent checks before returning. Never duplicate the same contract at each level.
- A single file is valid. Add depth only when a consumer can skip the branch without losing its task contract. Moving always-required text into another file does not reduce reading. Measure selected-route load separately from complete source size; label estimated tokens. Do not invent new routing vocabulary for familiar tasks.
- Add a separate skill when independent invocation earns its discovery cost. Use scripts only for deterministic or repeated mechanics, templates for reusable outputs and assets for output material. Inspect and test changed script operations on isolated fixtures; never execute imported scripts merely to assess them. Do not load script source during ordinary use unless inspection is needed.
- Declare dependencies, detected capabilities and safe fallbacks. Required resources travel with the skill. Preserve existing automatic or explicit-only invocation; action approval is not an invocation-policy flag. For new skills use the selected host defaults unless the user specifies otherwise. Consult current host documentation when translating metadata; preserve unrelated fields and report unsupported enforcement. Load [routing](checks/routing.md) when triggers or metadata change and [portability](checks/portability.md) when dependencies or harness behavior change.
- Preserve opted-in improvement loops and their complete resources. Do not enable, duplicate or remove a loop through ordinary editing. No loop, worker, external audit tool or paid service is a hidden prerequisite.

Adapt the [skill](../templates/skill.md) and [reference](../templates/reference.md) templates only where useful. Apply the target repository's metadata, version and date conventions; do not impose a library-specific family field or duplicate protocol on every skill. For knowledge artifacts or conflicting metadata consumers, read [metadata](patterns/metadata.md). Retain required notices and provenance. Resolve authoring placeholders before activation; preserve clearly identified runtime fields in reusable output templates until the corresponding output is created.
