# Task-selected navigation

Load from the primer recipe when designing nested maps. This pattern augments that recipe; return the selected route and gaps to it.

1. Give each map one declared navigation owner and stable, unambiguous source addresses. Preserve local naming and meaning. A child links to its parent; the parent links to the child. Independent references or shortcuts do not create a second owner.
2. A map contains enough purpose and route descriptions to choose the next source without reading every child. Link data, sites, procedures and skills by their use. A map earns a separate file through distinct context or lifecycle, not file count alone; it earns a separate skill through independent invocation.
3. Start at the requested map, including a supported shortcut. Before dependent work, resolve its required parent safeguards. Follow only the next relevant branch and return its result to the original task. A shortcut preserves canonical ownership and guard requirements; it does not silently bypass them.
4. Track the canonical node and remaining task. Returning to a parent is intentional. Repeating the same unresolved traversal without progress is a loop: stop, report the path and ask only for the ambiguity that matters. Do not impose a fixed structural depth or recursively preload descendants.
5. Missing or ambiguous required targets block their dependent route. An unverified source stays unverified; a navigation label does not establish its authority, currentness or access permission.

When adding a node, propose its owner map and both navigation links together. Repair only selected links through the existing write owner. Preserve authored groupings; a generated file dump is not a curated map. Share mandatory rules at their owner rather than copying them into every child.

Good: a deep entry can reach its ancestor safeguards and selected source while skipping unrelated bodies. Bad: backlinks cause recursive loading or a shortcut acquires weaker permissions.
