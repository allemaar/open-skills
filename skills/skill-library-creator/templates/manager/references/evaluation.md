# Check whether a skill helps

Load for new task behavior, changed triggers, substantial instruction edits or generated-manager upgrades. Reuse existing cases that exercise the change. Keep evaluation proportional: add a case only when it distinguishes a useful result from a plausible failure.

Use the [case template](../templates/evaluation.json) when reusable cases earn their upkeep. Store filled cases under the authored skill's `evals/`; keep sensitive inputs and run outputs in a permitted private location. The template is data, not a runner or evidence of passing tests.

1. Choose a realistic request and observable output requirements before running. Include a relevant missing-input or refusal case. For routing changes, add a request that should select the skill and a nearby request that belongs elsewhere. When changing a safeguard, reuse or add a case that plausibly tempts bypass; simulate hazardous effects. Check a materially different input when generalization from the development example is uncertain.
2. Run through an available host using the reviewed draft. Use fresh context when available; record carried context otherwise. Carry the assessment/authoring/evaluation context explicitly into fresh evaluation briefs so ordinary checks suppress improvement proposals; enable the loop only when that case specifically exercises it. Execute only inspected scripts within the requested scope. An evaluation does not authorize live publication, messages, destructive actions or provider changes.
3. Judge the resulting artifact or behavior against the criteria. Record pass, fail or not-observed with evidence and the actual harness/runtime used. An explicitly invoked skill tests behavior, not automatic selection. Report selection only when the host exposes it. If tools, invocation metadata or behavior differ across intended harnesses, exercise those differences on the affected harnesses and mark unavailable coverage untested. Installation targets are not compatibility evidence. Portable instructions alone do not require duplicate runs on every harness. When claiming efficiency, inspect available file reads, tool calls and time/token evidence for unnecessary work; leave unavailable measures unmeasured.
4. When claiming an improvement, compare the old version or ordinary no-skill workflow on the same inputs where practical. A check passed by both versions supports preservation; it does not alone demonstrate improvement. Prefer a clearly useful correction over a cosmetic score gain. Record unavailable comparisons without inventing a baseline or numerical confidence.
5. Report demonstrated weaknesses. If edits are authorized, follow [authoring](authoring.md) before preparing repairs, then rerun affected cases and relevant regressions. Report remaining gaps. After generator changes, exercise a generated manager independently through a representative operation and refusal; template hashes alone do not prove usability.

No particular model, subagent API, browser viewer, eval package or paid service is required. Manual artifact review is valid when labelled. Additional automated evaluation is optional.

For this manager's walkthrough and optional loop, adapt the bundled [manager cases](../templates/manager-evaluation.json). Supply user turns sequentially in the chosen host; case text is not execution evidence. Record observed opt-in, decline, silence, unanswered proposals and read-only behavior separately from static wiring checks.

Do: preserve task quality, correct refusal and understandable next steps. Don't: optimize only trigger wording, repeat expensive runs without new evidence, or call unobserved portability a pass.
