# Author and improve skills

For creation or authorized edits, read the [authoring contract](authoring-contract.md) before this procedure. Assessment-only requests use [assessment](assessment.md) without entering this write procedure. Editing an existing skill does not silently enable its improvement loop.

## Procedure

1. Read the existing skill and all affected constituents, references and known callers. Name exact files. Before replacing anything, inspect no-follow paths and save a no-overwrite preimage outside active discovery; recheck current bytes immediately before writing.
2. Start from the bundled [skill template](../templates/skill.md) and [reference template](../templates/reference.md), adapting sections to the task. For a new skill, ask once whether to enable [optional improvement proposals](self-improvement.md), unless already answered. Explain that concrete lessons can produce proposals requiring approval; declining adds no loop. If the user continues without choosing, keep it disabled and complete otherwise-authorized authoring; silence never enables it. Bundle its reference and closing route only if enabled. SKILL.md frontmatter contains matching name, family, skill-version (semantic version) and updated (actual local date). New skills start at 1.0.0; patch for compatible repairs, minor for compatible capabilities, major for breaking behavior. Imported upstream version is separate provenance.
3. Draft outside active discovery, for example in a permitted private staging directory, with references/scripts/templates as needed. Audit each instruction against the authoring contract, close every local reference/dependency and inspect scripts. Preserve required upstream licenses/notices; naming or compression never removes them. Supported loader metadata uses unquoted recognized keys, textual description, matching name/family, semantic version and ISO date; normalize unsupported YAML forms deliberately before publication.
4. Exercise one representative workflow and one meaningful refusal/failure case proportional to the operation. For new behavior, routing changes or generated-manager upgrades, load [evaluation](evaluation.md) for reusable cases and observed results. A formatter, syntax check or self-report does not prove behavior. For scripts, test their changed operation on isolated fixtures before using live targets.
5. Set the draft's matching name/family, semantic version and actual update date before activation. Preview `publish --library SKILLS --from DRAFT --name FAMILY-NAME --content-reviewed`. Apply with `--draft-expected DRAFT_DIGEST` from that reviewed preview; changed draft bytes require renewed review. For an existing skill also pass `--expected CURRENT_TREE_DIGEST` from the same preview's `currentDigest` (or read-only status's `sources` entry). The selected-skill preview works even when another sibling is malformed. Publication preserves the old complete tree, including constituents removed by the new draft. Update relevant provenance, run live inventory and selected local status, then reconcile only already-authorized installation scopes.

If that preview reports `currentMetadataError`, inspect the complete current tree and a no-overwrite preimage. Recover the intended next version from available provenance/preimages; do not invent version history. An explicitly requested metadata repair can use `--repair-metadata` with both reviewed digests and valid replacement metadata. A valid old semantic version still requires an increase. Missing or invalid old versions require this explicit repair path; unrelated valid skills need no repair flag.

For a new authored skill, origin is authored and revision is its first reviewed content identity; provenance may be a small sidecar. For updates, preserve the original origin and distinguish subsequent local changes. No fabricated version from an upstream source.

For an opted-in skill, copy the complete [improvement reference](self-improvement.md) into its own references directory as self-improvement.md, set `self-improvable: true` and add this closing route to its SKILL.md: “After this skill performs its own task, outside assessment, authoring, evaluation, import or publication, load this skill's references directory's self-improvement.md only for a concrete material or repeated lesson. Stay silent otherwise. Propose changes for user approval; never auto-apply.” The route, not the flag, supplies behavior. Declining a new skill's offer omits all three. On an explicit enable request, use the same wiring and a reviewed version bump; on disable, remove the flag/closing route and the copied reference if unused elsewhere. Preserve existing equivalent loops rather than stack another. An upstream import needs a reviewed variant before adding behavior. A plain improvement request means assessment/authoring; an explicit one-off loop request loads the reference without enabling future runs. Inventory's opt-in label reports the declaration, not observed execution.

Checklist: unique owner and trigger; prefix/name agree; output and failure criteria are concrete; conditional routes close; no duplicated rules; required resources bundled; relevant behavior exercised; version/date updated; links checked. Good: another agent completes the intended task with only its selected route. Bad: compression loses safeguards or a specialty forces unrelated context into every call.
