# Install, check and reconcile

Resolve this machine's physical library. Metadata-only `list` is independent of private installation state; malformed entries are reported without suppressing readable inventory. Use `status` for an explicit installation check, not generic help. Missing private configuration routes to the first-use walkthrough. An explicit check/install request may reconcile the remembered selected scope after reviewing current gaps; an inspection-only request stays read-only.

Use `configure --library SKILLS --scope global`, `--scope project --project PROJECT`, or `--targets JSON_ARRAY` for actual custom skill directories. Global locations are conventional candidates, not detected harnesses. Report existing and missing roots and let the user select them before creation. Preview exact source, targets and newly created roots; add `--apply` within the requested scope. Configuration is private and additive, so another project can be registered without silently uninstalling the first. Do not put personal target paths in shared library.json.

Run `reconcile --library SKILLS` before apply. Every active physical family-prefixed skill is considered even if it appeared since the last check. Invalid sources, ordinary directories/copies, unknown family entries and unavailable sources block the batch; report them rather than force replacement. Both `status` and `reconcile` accept `--targets JSON_ARRAY` to select a subset of already registered targets. State the selected scope; do not silently narrow a complete-check claim. To remove one registration while preserving its links, preview `configure --library SKILLS --targets JSON_ARRAY --unregister`, then apply with exact `--confirm TARGET`. Removed ownership rows are retained in a private recovery receipt; re-registering requires a fresh inspection.

`reconcile --apply` creates missing direct links, repairs only links whose current target matches this user's ownership receipt, and removes owned entries only for explicitly retired names. Before unlink, it records old and desired targets privately. It never follows a link during removal, deletes source contents or recursively cleans directories. Source and destination metadata/bytes are checked again before and after mutation. Preserve partial successes and recovery evidence if interrupted.

## Storage and native adapters

For the short recap, run read-only `status` with the selected targets and summarize its `summary` field. It distinguishes unconfigured, attention-required, changes-planned, matching-target and mutation-pending states. Counts describe the reviewed plan. Pending locks require inspection of active work or recovery; their age does not prove interruption. A preview does not verify linked bytes or runtime pickup; after apply, inspect fresh status and retain those evidence distinctions. Report an observed interruption with its exact receipt and locks, never as a completed install.

The library uses locally accessible filesystem bytes without owning synchronization. Network storage, local disks, OneDrive, Google Drive, Box, ordinary repositories and Lyt vault folders are eligible when their actual filesystem adapter passes the checks. A provider name or nearby repository marker does not prove capabilities, access or sync state. Virtual drives are capability-dependent. Active host policy may forbid an otherwise available adapter; report that boundary without bypassing it.

- The explicitly selected physical source, target and private-state roots establish confirmed boundaries; ancestor mounts are permitted there. Nested mounts remain rejected unless an additional relevant boundary is selected with `--mount-root ROOT`. Read-only inventory may cross mount boundaries. No boundary authorizes redirects or overrides host policy.
- For cloud placeholders, confirm the actual provider sync root with `--cloud-root ROOT`, or multiple independently confirmed roots with `--cloud-roots JSON_ARRAY`, and require readable local bytes. Microsoft CLOUD tags are supported; unknown reparse tags fail closed. Current-user OneDrive environment roots can supply candidates, but a folder name alone proves nothing. If hydration fails, request local availability and retry the exact read once.
- Windows defaults to direct directory junctions for local sources. Native drive-type inspection also rejects mapped network drives before mutation. UNC/mapped network sources require explicit `--link-type symlink`, available privileges and permission under host policy. Virtual drives remain capability-dependent; a local drive classification is not proof that creation will succeed. Windows PowerShell supplies drive-type inspection and the no-follow metadata fallback alongside fsutil. Never auto-elevate or change execution policy. macOS/Linux use direct directory symlinks. Verify the native link type, exact physical target and linked bytes.
- Refuse unsupported redirects, metadata or link capabilities. An unavailable source is not retirement and must never trigger an empty replacement library. Do not change accounts, provider permissions or sync settings to bypass a failure.

Receipts default to per-user application data (LOCALAPPDATA on Windows, Library/Application Support on macOS, XDG state/home on Linux); explicit private `--state` can support isolated tests or custom host paths. Keep it outside shared/source/target trees. Receipts record installation, not authorization certificates.

The running `mutation.lock` itself journals the operation: source mutations use a shared lock, local installations a private lock. Disruptive plans also receive private recovery receipts; there is no separate comprehensive transaction journal. An interrupted lock is retained and blocks new mutations. Load [operation-specific recovery](recovery.md) to inspect the exact operation, preimages and actual paths. Never discard it simply to retry. Source writers serialize through the shared lock; installation uses only this machine's private lock so read-only sources remain installable. A source writer on another private state can begin during reconciliation, even on coherent storage. Source rechecks may then stop a partial installation with retained receipts/locks; inspect recovery and obtain a fresh preview. These locks do not coordinate offline synced copies or provider conflict resolution.

After reconciliation, run read-only status and verify any affected skill's actual task. Exact target and linked bytes prove installation access, not runtime pickup. Report a reload/fresh-session requirement when needed. The manager cannot reconcile another machine merely by editing shared files.
