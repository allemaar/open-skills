# Upstream and manager updates

For an imported skill, inspect provenance.json and its retained baseline. Acquire the selected incoming revision using the import procedure, without executing it. Compare **original baseline**, **current pool version** and **incoming upstream version**, including dependencies, notices, scripts and naming history. Upstream mode preserves functional content; variant mode merges reviewed local improvements. Prepare the complete reviewed draft outside discovery, including its new version/date. Publish through the [authoring procedure](authoring.md) with the current tree digest, preserving the old complete tree. Update upstream baseline/revision separately from the pool's own version/date. A new upstream tag does not authorize silent replacement.

Use read-only `compare-upstream --library SKILLS --name FAMILY-NAME --from ACQUIRED_INCOMING [--revision REV]`. It requires no network or private installation state. The helper verifies portable ancestry (paths, types and file hashes), compares files/directories and rechecks complete native input snapshots. It reports unchanged, local-only, upstream-only, same-change and conflict, with additions/removals distinguished. Modes remain visible as separate permission review, including recorded executable bits; expected transport normalization does not corrupt content ancestry. These are file-level classifications, not a text merge or proof that independent changes compose safely.

For SKILL.md classification only, it aligns the four documented pool loader fields (name, family, skill-version, updated) to current values. Raw hashes and metadata remain visible. The manager-owned provenance.json is a separate review row, never silently discarded; incoming upstream provenance remains source evidence. Other naming/caller adaptations are real local changes. Inspect exact changed bytes, notices and dependencies before preparing a complete draft. A damaged/missing baseline blocks the automated comparison; do not invent ancestry.

New imports record `originalContentDigest`, its `path-type-sha256-v1` basis and original platform, alongside the full native `originalDigest` and `originalFiles`. Legacy provenance is read without mutation: verify its recorded native snapshot hash, then derive portable identity from those recorded rows. Missing/inconsistent original rows require reviewed ancestry recovery. Transport must preserve actual bytes; line-ending/content changes still require review. After a reviewed upstream update, retain a new complete unadapted baseline under `.library/upstream`, with these content/native digests, platform, original files/name/version and selected origin/revision. Update the draft's provenance to reference it while preserving prior provenance/baseline history. Keep old baselines. This is a guarded reviewed preparation step, not a side effect of comparison; publish the complete draft through the expected-digest check.

For the generated manager, locate an available inspected skill-library-creator version. The manager works without it for ordinary tasks; its absence blocks only this upgrade. Ask for the creator's physical location if unresolved. Run that creator's `upgrade --library SKILLS`, which compares managed-file baseline hashes with current customizations and incoming templates. Review differences, then pass its `--expected PLAN_DIGEST` with `--apply`. Changed incoming/current bytes or a changed render date require a fresh preview. Downgrades are refused; missing managed files and conflicts require the creator's manual merge procedure. Stored generator baselines must match their recorded hashes; drift requires reviewed ancestry recovery. Old baselines and library.json are retained with upgrade recovery. Per-skill copied improvement references remain skill-owned: assess differences after a manager upgrade, then offer any meaningful update through each skill's normal review and approval. Unrelated local files are preserved. The shared README is unmanaged after creation and needs separate review when setup guidance changes. Re-run source inventory and selected local status afterward.

Do not auto-download or run a new creator, reinstall a whole library, overwrite both sides of a conflict, or claim source sync changed teammates' installation settings. Success is a reviewed upgrade with preserved customizations, current provenance and readable recovery; failure is unreviewed behavior replacing the version users inspected.
