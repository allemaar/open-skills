# Existing installation methods

Load the matching route when method-specific provenance/comparison is needed. Its planning steps are read-only; apply only after the entrypoint's scope, write and recovery safeguards. Each route returns to the entrypoint's verification. Do not change methods to bypass a conflict.

## Direct links to a source checkout

Resolve the existing direct link and verify the physical checkout's origin, current commit, worktree/index and intended update mode. A shared checkout update affects every consumer linked to it. Enumerate links within the selected and inspected runtime/project roots, name that inspection boundary, and disclose that links elsewhere cannot be ruled out. Require selection of the exact physical checkout change with that shared effect and residual uncertainty before applying it; never claim a machine-wide consumer inventory from a bounded scan.

If it already matches the selected release, make no change. Otherwise fetch only the required public revision using existing Git tooling, then verify release/tag identity. Preserve the prior commit and a recoverable snapshot of changed source and link metadata. Include added, removed and changed skill/companion paths in the disclosed range: a whole-root link can expose additions automatically, and removed paths can leave existing links dangling. These effects retain their actual install/deletion gates. A checkout with edits, staged work, divergent or ahead history, or a private development branch is a conflict: leave it intact and return an explicit merge or isolated-release proposal. Do not detach a branch, switch tracking, repoint links or replace a working checkout without selection of those exact effects. For a clean owned release checkout, apply only the selected compatible fast-forward or approved release-selection operation, with precondition checks immediately before it. A pull of arbitrary main is not a pinned-release update.

Never write through an installed link, recreate a correct link or follow a nested redirect during writes. New/removed upstream skill names do not authorize creating or deleting runtime links. Report their exact migration set separately.

## Editable copies

Resolve the prior upstream version from verified owner state when present. The bundled installer may stamp SKILL.md metadata with github-repo, github-ref, github-tree-sha and github-path, or local-path; these unsigned hints must be checked against the actual source and represented file tree. Managed lock records retain their documented owner schema. An unstamped copy has no guaranteed version record. For one, use a user-supplied baseline or compare against a bounded set of named published releases; only an exact supported match establishes that baseline. Unknown customized content remains unknown. Do not invent provenance or write a new stamp merely to unblock the update. Retrieve verified old and selected release content into inspected staging with existing authorized Git/HTTP tools, then return to the parent scope/write checks before changing installed files. Compare old upstream, current installed content and selected upstream, including companions and installer metadata. Classify unchanged, local-only, upstream-only, both-changed, added and removed paths. Unknown baseline means unknown ownership, not permission to overwrite. Local absence is a local edit: keep local-only additions and deletions, and do not recreate a locally removed upstream file merely to match the release. Treat different local/upstream additions at the same new path as a both-added conflict. A locally removed required companion makes that installation partial; report it rather than silently restoring it.

Stage proposed content outside live discovery. Apply upstream-only changes and preserve local-only edits. For both-changed content, present a merge that retains local intent. Review every both-changed instruction/protocol for semantic conflicts even when text edits do not overlap, and keep live bytes until the user selects the exact merge with those conflicts resolved. A current instruction already selecting that exact merge satisfies this condition; do not ask again. Never replace a whole directory because some files are unchanged. Treat upstream removals as deletion candidates with their own exact gates; customized or unrelated files remain. Apply the same conflict rules to owner metadata. Leave conflicted metadata unchanged, and update supported provenance only for successfully installed represented files; do not advance a whole-installation claim across unresolved slices. If a trusted baseline or protected merge/write mechanism is unavailable, return the comparison and staged proposal without modifying that slice.

## Managed plugin or installer

Identify the actual manager, lock/provenance record, installed package and any local overrides. Read its current documented scoped update operation and inspect its effects before using it. Reuse the existing owner, not a second installer or manually edited cache. Preserve exact package/metadata preimages and establish how overrides survive; a manager with no safe preservation path blocks that customized update.

Run only a command scoped to the selected open-skills installation. If the owner cannot pin the requested release, the selected operation may update unrelated packages, or silently discards edits, stop and propose the smallest supported alternative without executing it. Preserve existing telemetry settings; updating does not authorize directory-ranking submissions or new telemetry. Keep the owner's provenance format intact and verify actual consumed state afterward. Establish recovery through the owner's supported prior-version operation when available. Saved cache/package preimages are evidence, not permission to edit a managed cache by hand; unsupported restoration needs a separately selected recovery operation.
